# 출석 설계와 검증 계획

**AI가 작성한 제안이며, 동작하는 출석 시스템은 아직 없다.** 교시 시각과 외출 복귀 예외는 사용자가 제공했다. 참여자, 실제 하드웨어, 확인 담당자·권한과 세부 운영 절차는 미확정이다.

## 사용자 제공 시간표

2026-11-16 대화에서 사용자가 제공한 야자 시간표다. 저녁 시각으로 해석해 `Asia/Seoul`의 24시간제로 기록했다. 학교 공식 문서를 별도로 검증한 것은 아니다.

| 교시 | 시작 | 종료 | 길이 |
|---|---|---|---|
| 1교시 | 18:25 | 19:20 | 55분 |
| 2교시 | 19:30 | 20:20 | 50분 |
| 3교시 | 20:30 | 21:20 | 50분 |

교시 사이에는 각각 10분 휴식이 있다. 적용 요일·날짜·시간표 예외는 아직 정하지 않았다. 2026-11-17 사용자가 제공한 구매 링크로 **AS608, F-F 점퍼선, microSD, Raspberry Pi Zero 2 W(with Headers)**를 식별했으나 이후 **라즈베리파이 주문 취소**를 보고했다. 사용할 중심 보드는 미정이다. [부품 목록](HARDWARE_INVENTORY.md). 센서 실물 사양·핀 배치·전원·통신·보드 부팅·인식 동작은 미확인이다. 노트북의 가상 데이터로 출석 규칙을 먼저 검증하고 실제 센서 연결·부팅은 사용할 장치가 정해진 후 진행한다.

## 초기 범위 — 시각 제한 없는 하루 한 건 출석

사용자 최신 요구는 **언제든 하루 한 번 출석할 수 있게 하는 것**이다. 학생별 날짜별 출석·지각·미확인 명단과 그 범위의 알림만 설계한다. 하루는 `Asia/Seoul` 기준 해당 날짜 00:00 이상, 다음 날짜 00:00 미만이다. 2·3교시는 시간표 참고 정보이며 별도 출석 의무·미출석 상태·알림을 생성하지 않는다. 그 시간의 첫 인식도 당일 출석으로 받되 외출 예외를 확인한 뒤 지각 여부를 정한다. 하루 한 번의 출석을 야자 전 시간의 재실 확인으로 간주하지 않는다.

이 결정은 이전의 18:10 접수 시작 제한을 대체한다. **해당 날짜 18:25 정각까지 정상 출석, 그 이후 첫 인식은 지각 여부 확인 대상**이다. 시각 때문에 당일의 첫 출석을 거부하지 않는다. 첫 유효 인식으로 만든 기록은 재인식으로 추가 생성하거나 시각·상태를 덮어쓰지 않는다. 담당자가 외출 예외를 확인하거나 정정하는 경우는 별도 감사 이력으로 관리한다. 자정을 넘긴 인식은 새 날짜의 기록 대상이며 전날 출석을 자동 보충하지 않는다.

## 외출 복귀 예외와 미확인 학생 확인

사용자 설명: 기숙사 학교에서는 외출 후 돌아오자마자 출석한 학생을 지각 처리하지 않는다. 야자 출석 때 보이지 않는 학생은 다른 학생들이나 사감 선생님을 통해 상황을 파악한다. 지문 인식 시각만으로 외출 여부·복귀 즉시 출석 여부를 알 수 없으므로 시간 판정과 최종 상태를 분리한다.

후속 사용자 답변으로 **미확인 명단은 18:25에 바로 확인**하기로 했다. 이때의 명단은 현재 상황 확인용이며, 출석 접수를 닫거나 결석·지각을 자동 확정하는 시점이 아니다. 이후 지문 인식·사유 확인·정정이 들어오면 명단을 갱신한다.

예외는 외출 복귀에 한정하지 않는다. **사용자에게 따로 사유를 알려준 학생**도 확인 대상으로 관리한다. 사용자가 해당 사유의 예외 처리를 확인하면 그에 맞게 상태를 정정한다. 이유를 알렸다는 사실, 실제 지문 출석 여부, 지각 면제 여부는 서로 구분한다. 지문이 없는 학생을 사유만으로 출석 완료로 만들지 않는다. 구체적인 병증·상담 내용 대신 ‘사유 확인’ 같은 최소 구분을 기록하며 담당자 계정·권한은 학교 운영 승인에 맞춰 정한다.

| 확인된 상황 | 상태·처리 제안 |
|---|---|
| 18:25 정각까지 첫 인식 | 정상 출석 |
| 18:25 이후 첫 인식, 사유 미확인 | 출석 시각 기록, 지각 여부 확인 필요 |
| 외출 복귀 직후 출석한 사실 확인 | 출석(외출 복귀), 지각 제외. 실제 늦은 인식 시각은 그대로 보존 |
| 확인 결과 외출 복귀 등 예외 없음 | 지각 확정 |
| 출석 기록 없음, 상황 모름 | 미확인. 학생들이나 사감 선생님을 통해 확인 |
| 아직 외출 중인 사실 확인 | 외출 중(확인). 출석 완료나 결석으로 자동 변환하지 않음 |
| 사용자에게 따로 알려준 사유가 확인됐고 아직 인식 없음 | 사유 확인(출석 미기록). 미확인과 구분하되 출석 완료로 바꾸지 않음 |
| 늦은 인식에 대해 사용자가 사유에 따른 지각 면제를 확인 | 출석(사유 확인), 지각 제외. 인식 시각·확인자·변경 이력 보존 |

학생이 알려준 내용과 담당자가 확인한 내용을 구분한다. 상태를 확정·정정하는 담당자 권한과 확인 방식은 학교 운영에 맞춰 정한다. ‘복귀 직후’를 임의의 몇 분 규칙으로 만들거나 복귀 시각을 추정하지 않는다. 확인 전 지각·결석을 확정하거나 불이익 알림을 보내지 않는다. 하루 한 건 제한은 출석 중복 생성을 막는 규칙이며, 확인 후 같은 기록의 상태를 정정하는 것은 허용한다.

저장 항목은 인식 시각, 상태, 외출 복귀 등 최소 사유 구분, 확인 여부·확인자·변경 이력 중심으로 설계한다. 친구를 통한 확인을 정밀 위치 추적이나 상세 외출 목적 수집으로 확대하지 않는다. 실제 외출 기록·학생 정보는 Git에 넣지 않는다.

## 처리 경계

1. **식별 어댑터**: 센서 내부 매칭 가능성을 검토하고 앱에는 가명 학생 ID와 성공/실패 결과만 전달한다. 원본 지문 이미지나 특징정보를 앱·GitHub로 내보내지 않는 구조를 우선 검토한다. 장치 사양 확인 전 지원 기능으로 단정하지 않는다.
2. **시간 판정**: 학교가 승인한 서버/기기 시계와 `Asia/Seoul` 기준 1교시 시작 18:25를 사용한다. 단말 시각 오류·오프라인 재전송은 검토 대상으로 남긴다. 수신 시각과 인식 시각의 차이를 기록하고 지연 이벤트의 처리 정책을 정한다.
3. **출석 기록**: `(한국 시간 날짜, 가명 학생 ID)`를 논리적 유일 키로 사용한다. 같은 날짜의 첫 유효 인식만 출석 기록을 생성하며 중복 스캔·재전송·동시 요청에도 한 건만 유지하도록 설계한다. 첫 기록은 정상 재인식으로 변경하지 않는다. 오프라인·신뢰할 수 없는 기기 시각은 별도 검토 대상이다.
4. **명단 조회**: 해당 날짜의 야자 참여 대상에서만 명단을 구성한다. 외출·면제·수기 확인·정정 이력을 반영하고, 권한 있는 담당자가 필요한 날짜의 명단만 조회한다.
5. **알림 큐**: 기본은 미리보기. 미확인 명단은 18:25에 바로 확인하며 하루 종일 출석을 받는 것과 별개다. 최종 알림 검토·전송 시점은 아직 정하지 않았다. 명단 확인 후에도 첫 인식은 접수하고 외출 등 사유 검토에 따라 명단·미전송 알림을 갱신한다. 미확인 학생의 상황 파악과 최종 미출석 통보를 구분하며, 외출 중·사유 확인·확인 대기 상태를 결석으로 통보하지 않는다. 담당자 확인·승인된 수신자가 정해진 뒤 최소 정보로 보내는 후속 기능이다. 이번 세션에서는 실제 메시지를 보내지 않는다.

## 확정 규칙과 미확정 정책

| 항목 | 상태·제안 |
|---|---|
| 정각/지각 | 해당 한국 날짜 18:25까지 정상 출석. 이후 첫 인식은 지각 여부 확인 대상이며 외출 복귀 직후 출석이면 확인 후 지각 제외 |
| 사전 인식 | 시각 제한 없음. 18:10 이전도 당일 첫 유효 인식이면 정상 출석. 과거 15분 제한은 폐기 |
| 출석 접수 구간 | 한국 시간의 달력 날짜 전체. 매일 00:00에 날짜가 바뀌며 별도 접수 마감 시각을 두지 않음 |
| 다음 날 인식 | 다음 날 출석 대상으로 판정. 전날 출석을 자동 보충하지 않음 |
| 중복 인식 | 정상 재시도로 출석을 추가 생성하거나 최초 정시 출석을 지각으로 덮어쓰지 않음. 원 이벤트와 정정은 감사 가능하게 구분 |
| 미출석 | 18:25에 바로 `미확인` 명단 확인. 사용자가 이미 전달받은 사유, 학생들이나 사감 선생님을 통한 상황 파악, 외출·면제·대체 출석·장애를 반영한 뒤 판단 |
| 센서 실패·정전·시계 오류 | 결석으로 자동 확정하지 않음. 수기/대체 확인과 정정 경로 제공 |
| 알림 | 학교가 사생회 수신 범위·권한을 승인해야 실제 전송 가능. 전송 재시도에도 동일 알림이 중복되지 않도록 키·전송 상태 관리 |
